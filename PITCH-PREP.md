# KhojSetu: understand it, explain it, demonstrate it

## Start here: what did we build?

KhojSetu is a field notebook that can search the meaning of archaeological observations on a laptop without internet. When a researcher chooses to connect, it exchanges approved records with a shared team archive.

**One sentence to remember:** “KhojSetu helps archaeological teams record discoveries, retrieve related evidence offline, and exchange approved knowledge when connected.”

**The original problem statement is from Qdrant.** It asks for an edge memory and intelligence platform. Archaeology is the application domain we chose; the challenge itself did not prescribe archaeology.

**Edge device** simply means the computer being used in the field. For our demo, that is this laptop. **Semantic search** means searching by meaning. **Synchronization** means exchanging changes between the field computer and shared storage.

## The example you should tell

Imagine a researcher finds a small decorated pottery fragment in an excavation trench. A colleague previously described a similar object as a “painted ceramic shard.” The researcher wants to compare the observations immediately, but the internet is unavailable.

They record the finding in KhojSetu and search “decorated pottery with geometric patterns.” The local model represents the meaning of the words. Qdrant Edge retrieves related records already on the device. The researcher can narrow the results to the same excavation layer and inspect the original notes.

Later, the researcher approves the finding for sharing. When they enable and start an exchange, the application checks its policy, sends eligible records to the team archive and downloads shared changes. If two researchers edited the same record, it shows both versions for human review.

## Why archaeology?

The value of a find includes its context: location, layer, depth and surrounding observations. A pottery fragment with no recorded context is less useful for interpreting the excavation. The Archaeology Data Service explains that excavation changes or destroys original in-place evidence, making preservation of its records especially important [1].

Our reasoning for choosing this domain:

| Qdrant challenge need | Archaeological example |
| --- | --- |
| Useful offline operation | Search earlier field notes while disconnected |
| Semantic retrieval | Relate “pottery,” “ceramic fragment” and descriptions of surface decoration |
| Metadata filtering | Limit results to grid B12, layer L3 or ceramic material |
| Selective sharing | Keep sensitive or unapproved observations local |
| Evolving information | A specialist revises an earlier description |
| Conflicting edits | Two field units update one shared record independently |
| Edge-to-server workflow | Exchange field discoveries with a shared research archive |

**If asked why not a general-purpose app:** “We chose a specific workflow so the value is demonstrable. Archaeology lets us show meaning, physical context, privacy and changing interpretations together. The underlying memory and exchange approach could later support other field teams.”

Do not claim every excavation lacks connectivity, that archaeologists have no existing software, or that our solution replaces archival standards. These are conditions the product is designed to handle. Domain fit still needs validation with practitioners.

## Understand the dataset

The demo currently contains **40 synthetic records**: 15 ceramic, 10 stone, 5 metal, 4 bone, 4 organic and 2 other material records. These are illustrative examples created for the prototype, not discoveries obtained from an archaeological authority. They are stored in `backend/demo.json`; the backend loads them into real local storage and creates real vectors.

The model is pretrained. **We did not train a model on these 40 records.** We used a downloaded MiniLM model to turn each record's text into a vector and indexed those vectors in Qdrant Edge.

Example visible in the app:

| Field | Example | Meaning |
| --- | --- | --- |
| Title | Painted Ceramic Fragment | A human-readable name |
| Record ID | ARC-970532CA in this installation | Unique label for the entry; IDs differ after a fresh seed |
| Material | Ceramic | What the object is made from |
| Grid | B12 | The square where it was recorded; B is the row and 12 the column |
| Layer | L3 | The recorded excavation layer; this is not an age prediction |
| Depth | 1.8 m | Recorded depth in the synthetic example |
| Field notes | Red fragment with triangular decoration | The researcher's observation |
| Priority | High | A user-assigned flag used by exchange policy |
| Approval | Approved | The entry is allowed to be considered for exchange |

The drawings are illustrative specimen sketches. They are not photographs of real finds or measurements generated by the system. The grid is schematic; it is not GPS mapping. Period labels in the source demo data are fictional context, not validated dating.

At preparation time, 35 records are pending and 5 are local-only because the seed marked records approved with automatic visibility, and policy shares high/medium priority while retaining routine records. Counts change as you edit or exchange.

## Understand the six screens

| Screen | What you do | What to say |
| --- | --- | --- |
| Field station | Select a layer and grid cell; open a finding | “This puts field memory back in its excavation context.” |
| Memory archive | Browse records and filter them | “These are the observations stored on this device.” |
| Ask the archive | Search by meaning, lexical terms or both | “The model and Qdrant Edge retrieve records locally.” |
| Record a finding | Enter notes, context, priority and sharing choices | “The new observation is saved and indexed on this device.” |
| Knowledge exchange | Enable exchange, send/receive changes, resolve conflicts | “Only eligible records leave the device through this workflow.” |
| System & activity | Inspect the engine information and action history | “We make the memory and exchange process visible.” |

**Status labels:** LOCAL ONLY = retained here; PENDING = eligible change waiting for exchange; SYNCED = last exchanged version acknowledged; CONFLICT = local and shared changes need review. A synced record can become pending again after editing.

**Field mode** deliberately pauses exchange. It does not disconnect the laptop's Wi-Fi. The local app still needs its Python process running. A real internet outage also allows local retrieval because the model, records, interface and engine are already on the laptop.

## Where is Qdrant, and what does the backend do?

```text
YOUR LAPTOP
Browser notebook
    → Python API: validates and saves the record
    → Local MiniLM model: text becomes 384 numbers
    → Qdrant Edge: stores vectors and retrieves related records
    ↔ SQLite: records, versions, queue state and activity

WHEN YOU START AN EXCHANGE
Sharing policy → version-aware exchange gateway → Qdrant Server
                      ↑                              ↓
                conflict review ← shared changes ← team archive
```

Those 384 numbers are a learned representation of text. Nearby vectors often correspond to similar meanings. They do not independently prove archaeological relationships or facts.

| Component | Concrete job | Evidence to show |
| --- | --- | --- |
| Local model | Produces dense semantic embeddings offline | System & activity shows MiniLM model name |
| Qdrant Edge | Stores dense and sparse vectors and runs local retrieval | Search screen shows real results and measured elapsed time |
| SQLite | Keeps record bodies, pending state, versions and history | Save a record; observe its status/activity and persistence |
| Policy function | Checks approval, sensitivity, visibility and priority | Show a local sensitive record versus an approved high-priority record |
| Exchange gateway | Checks revision numbers and avoids duplicate retries | Run exchange; show a conflict if two units changed the same record |
| Qdrant Server | Persists shared vectors and payloads | Open its dashboard and inspect the shared collection |

Hybrid search combines **dense semantic retrieval and lexical sparse retrieval**, then combines their rankings using reciprocal-rank fusion. The current lexical encoder uses term frequencies; do not call it BM25. Qdrant performs the underlying searches; our application combines the ranked results.

The assistant currently extracts original notes with source IDs. It does not call an external generative model. That keeps its answers tied to the recorded evidence.

The shared server runs in Docker on this laptop for the demo. Docker packages the server and its dependencies. This demonstrates real client-server exchange, but **it is not a deployed external cloud**. Qdrant Cloud can be configured later. No account is required now.

## A three-minute pitch you can read aloud

“Imagine finding a decorated pottery fragment during fieldwork. You want to know whether your team has seen something similar, but earlier notes are scattered and the internet is unavailable.

We built KhojSetu—Discover, Remember, Connect—a local semantic memory system for archaeological field research.

The Qdrant challenge asks for an application that remembers and retrieves on an edge device, works offline, handles changing information and exchanges knowledge intelligently. We chose archaeology because a discovery depends on its context: where it was found, which layer it came from and how it relates to earlier observations.

In KhojSetu, researchers record the object and its context on their field laptop. A local embedding model represents the text, and Qdrant Edge stores and searches it. A query such as ‘decorated pottery’ can retrieve related descriptions such as ‘painted ceramic fragment.’ We can also filter by excavation layer or material.

Sharing follows explicit rules. Sensitive and unapproved records remain local. Approved findings can enter the exchange queue according to their priority and visibility. When the researcher starts an exchange, eligible records go through our version-aware gateway into Qdrant Server, and shared changes come back to local memory.

If two researchers changed one record, we preserve the disagreement and ask them to choose or keep both notes.

Our demo uses 40 synthetic records. The local embedding, Qdrant Edge retrieval and Qdrant Server exchange are real. The current server is hosted locally for demonstration, and the evidence assistant quotes recorded observations.

The proposed value is less time searching for relevant field evidence, continued work without connectivity and clearer coordination between teams. Our next step is a small pilot with an excavation team to measure those outcomes.

KhojSetu helps a field device carry useful memory, then connect that memory with the team.”

## Click-by-click demo: about five minutes

Open the animated explanation at http://localhost:8000/pitch.html. Press **Play story**, or use **Next** while you speak. It is a conceptual explanation, not a live monitor. Then open the actual app at http://localhost:8000.

### 1. Show an existing observation — 40 seconds

Field station → L3 → grid B12 → Painted Ceramic Fragment. Point to title, grid, layer, depth and notes. Say: “These 40 records are synthetic; their storage and retrieval are real.” Close the record.

### 2. Retrieve evidence locally — 50 seconds

Ask the archive → enter `decorated pottery with geometric patterns` → choose Semantic or Hybrid → choose L3 → Search memory. Open a result. Say: “Qdrant Edge found related stored observations. The layer is a metadata filter.”

Click Review evidence if time permits. Explain that it extracts the original notes and references the records. Timing is measured for this query; do not promise a fixed production latency. Similarity and ranking scores are not probabilities of correctness.

### 3. Create your own record — 60 seconds

Record a finding. Enter:

- Finding: `Demo — painted vessel fragment`
- Material: Ceramic; grid: B12; layer: L3; depth: 1.85
- Notes: `Synthetic demonstration: red ceramic fragment with a triangular painted band, recorded beside the trench wall.`
- Descriptors: `ceramic, painted, geometric`
- Visibility: Automatic; priority: High; check researcher approval.

Save. Its status should be pending. Search for `triangular painted band` and find it locally. Explain that it was saved, embedded and indexed immediately.

To show privacy, edit that same record and mark it sensitive. Save: it becomes local-only. Before sending a sample to the server, clear the sensitive flag deliberately and retain approval. This demonstrates the policy with synthetic data.

### 4. Show a real exchange — 60 seconds

Knowledge exchange → Enable exchange → Exchange now. Enable is permission for connection attempts; Exchange now actually performs the request. Show uploaded/received counts. Then open http://localhost:6333/dashboard → Collections → `khojsetu_shared_v1` → inspect a point and its payload. Find the demo title or record ID. This database is Qdrant Server; private Edge records live elsewhere.

If the dashboard labels differ, use its collection list and select the named collection. Do not spend the pitch typing vectors or opening raw database folders.

### 5. Finish on activity and architecture — 40 seconds

System & activity → point to the engine, model and exchange event. Return to the animated architecture for your closing line. Keep the two-device conflict demonstration as an optional extension if the judges ask; instructions are in START-HERE.md and it was exercised in integration tests.

**If exchange fails:** say “The server is unreachable, so the changes remain queued.” Show that local search still works. Restart the container/gateway after the presentation. Do not describe a failed transfer as successful.

## Business and impact: a proposal to validate

The user is the field archaeologist or supervisor. Potential institutional buyers include university excavation programmes, archaeological consultancies and heritage research organisations. These are proposed customer groups; no customer interviews, contracts or partnerships have been established here.

| Proposed benefit | Why it could matter | Pilot measurement |
| --- | --- | --- |
| Faster retrieval | Researchers find relevant earlier notes while recording | Time to locate a known related observation, compared with current workflow |
| Continued work offline | Recording and retrieval do not wait for cloud access | Successful record/search tasks during planned disconnection |
| Better team handover | Approved observations move between units | Time from approved finding to availability on another unit |
| Clearer disagreements | Conflicting changes are visible | Conflicts preserved and resolved without silent overwrite |
| Controlled exchange | Sensitive/unapproved records remain local | Policy audit: number of ineligible records transmitted should be zero |

**Possible business model:** paid institutional deployment/support, annual site/team licensing and optional hosted coordination. Price after a pilot; do not invent a market size, revenue forecast or percentage saving. Local inference avoids a per-query hosted AI bill, but hardware, maintenance, hosting and support still cost money.

**First validation step:** work with one small field team, use approved sample data, compare retrieval with its existing process, and assess terminology, record quality and workflow fit. The product should complement established recording and archive practices.

## Questions judges may ask

**Why Qdrant Edge instead of just SQLite?** SQLite keeps structured records and transactional state. Qdrant Edge supplies the vector retrieval engine. We use each for its intended role.

**Why Qdrant Server too?** It stores shared vectors centrally so approved knowledge can be exchanged between field units. It is optional for local search.

**What is your innovation?** The combination of on-device semantic retrieval, excavation context, explicit memory policy, durable exchange and version conflict review in one field workflow. These components are not claimed as new inventions individually.

**Is it actually offline?** Once installed and the model is cached, local recording and search need no internet. The Python service must run locally. Field mode is an application control; it does not turn off Wi-Fi.

**Does it identify or date artefacts automatically?** No. It retrieves related descriptions and preserves human observations. It does not provide validated typology, authenticity, age or cultural attribution.

**How intelligent is the sharing?** It is a transparent rule engine using sensitivity, approval, visibility, priority and a limited-link option. It is not a learned classifier. Both the decision and reason can be shown.

**What happens if the connection fails halfway?** Unacknowledged changes remain pending. The gateway uses event IDs for repeat requests and revision checks to detect competing edits. Local storage remains usable.

**What if two people change the same record?** A different shared revision produces a conflict instead of a silent overwrite. Users inspect both versions and keep local, use shared or keep both notes.

**What does a score mean?** A ranking value: dense cosine, lexical term score or hybrid fusion score. It is not an archaeological confidence level.

**Is this trained on real archaeological data?** No. It uses a pretrained text model and 40 synthetic demonstration records. A domain pilot and expert evaluation remain necessary.

**Are photographs searched?** No image embeddings or synchronized attachments are implemented. Current retrieval is text-based; the visible drawings are illustrations.

**What is still incomplete?** Automatic reconnect exchange, production access control, real field validation, image retrieval and large-scale performance evaluation. The current implementation is a single-team local demonstration with manual exchange.

**Why can I see a database dashboard without a login?** It runs on this laptop, bound to localhost. An externally hosted installation would need proper access controls and HTTPS.

**What changed from the initial repository?** The initial code ran local browser storage, weighted matching and simulated synchronization. The new active interface connects to a Python backend, real embeddings, Qdrant Edge, SQLite and a real Qdrant Server exchange gateway.

## Technical proof for a judge who wants code

Use this only if asked; do not read code during the main pitch.

- `backend/vectors.py`: `EdgeShard.create/load`, real `upsert` and `query`, local `TextEmbedding`.
- `backend/models.py`: the `policy` function and input fields.
- `backend/store.py`: persistent records, exchange, pending changes and conflict resolution.
- `backend/cloud.py`: Qdrant Server collection creation/upserts and revision checks.
- `backend/app.py`: the local API used by the frontend.
- `backend/test_integration.py`: real-engine tests covering retrieval, privacy, failed exchange, two devices/conflicts and restart recovery.
- `compose.yaml`: starts the Qdrant Server container.

The localhost setup has passed a production frontend build, type-check and five integration tests. A browser query measured 17.7 ms once on 40 records; this is a small-data observation, not a benchmark claim.
